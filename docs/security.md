# Local trust and isolation audit

This is a development release candidate, not a security certification or a production service. The tested boundary is one Linux guest on Apple Virtualization through external Lima 2.2.1. A malicious guest kernel, hypervisor escape, hostile host user/root, malicious runtime/build tools, or compromised dependency is outside the established protection. No penetration test or independent audit has been completed.

| Surface | Default and practical boundary |
| --- | --- |
| Host files | No host home/project mounts, additional disks, automatic copy-to-host or inherited Lima templates. A VM receives its virtual disk, provisioning data and explicitly copied bytes only. The host CLI itself runs as your macOS user and can read files that user can read; it is not an OS-sandboxed app. |
| Devices | Virtual CPU/RAM/disk/network through VZ; no camera, microphone, USB, host display/input, Rosetta or audio sharing configured. The guest desktop is Xvfb, not the Mac WindowServer. Virtual devices still expose hypervisor attack surfaces. |
| Credentials | Per-machine generated application key, guest host key and separate Lima bootstrap administrator identity in private state. No host SSH agent, user's ~/.ssh keys, cloud/API credentials or proxy environment forwarded. Lima subprocess HOME/LIMA_HOME/TMPDIR point inside the selected private namespace. Host PATH remains a trusted executable boundary. |
| Network | Explicit NAT only. Outbound Internet and possible host/LAN access remain possible. NAT is **not** an egress firewall, tenant isolation or a guarantee that guest services cannot be reached. Do not expose sensitive host/LAN services to an untrusted guest. No offline/restricted-network feature is advertised. |
| Host listeners | Lima's management SSH endpoint on loopback; application control also uses that endpoint. No separate product daemon/network listener by default. `view` opens an authenticated 127.0.0.1-only HTTP viewer only when fallback is selected; no lifecycle/input APIs are exposed there. MCP uses stdio. No LAN/cloud listener option. |
| Port forwarding | `plain: true`, empty port rules, no inherited overrides. Lima plain mode disables dynamic forwarding, with static rules still possible; ours supplies none and validates/seals effective configuration. See the [official Lima port documentation](https://lima-vm.io/docs/config/port/). Bootstrap SSH is necessary management, not a forwarded guest application port. |
| Clipboard/input | Unicode paste uses only the Linux user's X11 clipboard. No host clipboard reading/writing, OSC52 forwarding, pointer injection or host desktop fallback. Human CLI exec output escapes control characters. Guest programs can read each other's guest clipboard/display because they share the X11 user/session. |
| Privileges | Host CLI/runtime run as your user without sudo; VZ authorization/entitlements are supplied by the external runtime. Provisioning and explicit packages maintenance use guest root via the private Lima admin account. The guest service runs as non-sudo `agent`, with NoNewPrivileges, systemd write boundaries, delegated process cleanup and umask 0077. The guest agent can run arbitrary commands/read that guest user's data, not a sandbox for separate hostile tasks. |
| Application channel | Host-key-pinned, batch-only SSH, forced restricted command, no SSH/X11/agent forwarding, then guest Unix socket under /run/agent-linux (0700 directory, 0600 socket). Hello/session/probe identity checks; bounded JSON, strict schemas/duplicate rejection, timeouts/output limits. Guest service peers share guest-user trust, not separate per-agent identities. |
| Bootstrap | Lima bootstrap management trusts its generated private namespace and uses weaker SSH host enrollment than the separately pinned application channel. Host-generated guest host-key material remains in the private provisioning template/state. Do not publish/attach state or raw Lima logs. A hostile runtime can subvert this trust. |
| File copies | Host operator chooses every source/destination. Bounded bytes, no mounts, no host archive extraction, no guest-selected host destination or automatic execution. See [file transfer](file-transfer.md). Hashes catch corruption/changes; a compromised guest can manufacture its own data/hash and lie about task results. |

A malicious guest process can attempt to phish the agent through screen content, steal guest credentials/project files, read the shared guest display, exhaust the bounded VM disk/RAM, attack reachable network services, return malformed messages/PNG/files, or exploit the runtime/hypervisor. Protocol limits, no host shares and host output validation reduce specific risks; they do not establish a hostile-code security guarantee. Agent instructions about untrusted page text are workflow guidance, not an enforcement boundary.

All local tools/MCP clients given machine access are trusted with powerful guest access. The explicit host file-copy, reset/delete and package-maintenance surfaces are operator CLI commands, not new MCP tools. File operations never fall back to a host shell. Unsupported operations on older guests fail visibly; there is no implicit disk upgrade.

Private state is 0700 with owner/marker/path checks and 0600 control files. Effective machine configuration is checked against its generated recipe and sealed hash before control. These checks resist mistakes, unsafe overrides and guest-controlled paths; they do not defend against another process with the same host UID changing files concurrently. Back up wanted guest results before reset/delete. Secure erasure on APFS/SSD, old backups, swap, snapshots and recovery of deleted bytes are not promised.

No host path-sharing mode is implemented. This makes the only opt-in host data access an explicit one-way copy of a selected regular file. No enforceable network isolation is offered, so no untested firewall setting is described as protection. A future isolation feature must test actual host/LAN/Internet denial, DNS/IPv6 behavior, reboot persistence and management-channel access before advertising it.

## Phase 6 additions

Human viewer input is guest-only. No host pointer, clipboard read, home/project mount or host shell is added. A 15-second ownership lease serializes cooperating frontend mutations; same-UID host processes and guest X11 applications remain trusted within their existing boundaries. Disconnect/generation change requires fresh observations and explicit ownership recovery. Local NAT still permits host/LAN reachability.

Cloud development bearer identities are random, hashed server-side, eight-hour expiring and workspace-scoped. Private client files contain credentials and must stay outside Git. Control plane binds only literal loopback, checks ownership on every session route, denies browser origins, bounds messages/rates/in-flight work and redacts errors. No production identity or public deployment is provided. Optional SDK credentials stay server-only; screenshots/input never enter audit logs. Provider network controls are requested but not empirically validated; [cloud threat boundaries and cleanup gates](cloud.md) are mandatory before untrusted use. Limits are not a perfect financial cap.

## Phase 7 payment boundary

Server-only Stripe test key/signing secret are environment values, never guest/client configuration or persisted state. Hosted Stripe fields collect test card data; our API has no raw card endpoint. Live/restricted keys, live config/objects/events, connected-account webhooks and automatic collection are rejected. SDK diagnostics/payloads are suppressed; account-authorized CLI output can intentionally show a private hosted setup/portal/invoice URL. Do not put those links in public logs.

Webhooks verify exact raw bytes, signature/timestamp and SDK API version, persist only a minimal receipt, then reconcile current associated objects. Ledger write failure closes admission while owned provider cleanup is still attempted. Spending caps allow cleanup/billing lag and are not perfect provider spending guarantees. Financial history is private and bounded; production storage, authorization separation, archival/retention and independent reconciliation remain unaccepted. See [billing](billing.md).
