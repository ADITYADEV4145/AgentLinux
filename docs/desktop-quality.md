# Modern desktop selection and actual evidence

Evaluated **2026-11-05**. Recommendation: **Ubuntu 26.04.1 LTS, ARM64, Ubuntu's GNOME 50 Wayland desktop**, with a quality-oriented starting VM profile of **4 vCPUs, 8 GiB RAM and a 40 GiB persistent disk**. With the existing at-most-half-host-RAM policy, an 8-GiB guest implies at least 16 GiB host RAM; the tested Mac has 24 GiB. No smaller-host support claim follows. This is the proposed next desktop target. The shipped 0.5.0-rc.1 backend remains **Debian 13/Xfce/X11** until GNOME passes the complete control/MCP/viewer acceptance below. No existing machine/template was migrated or reset for this evaluation.

The goal is a coherent Linux computer: launcher/workspaces/windows, file manager, terminal, settings/editor/browser, normal application installation, updates and persistent user data. Choosing an old session solely to conserve RAM does not satisfy that product goal. The existing Xfce setup has useful applications and tested controls; its current visual experience is not the desired GNOME target.

## Selected app set and exact running prototype

Actual VM: **Ubuntu 26.04.1 LTS (Resolute Raccoon), arm64**, kernel **7.0.0-34-generic**, GNOME Shell **50.1** (Ubuntu package 50.1-0ubuntu1.5), Mutter **50.1-0ubuntu2.5**, Wayland, 1280×800, scale 1. Booted on this ARM64 macOS **26.5 (25F71)** / 24-GiB Mac through **Lima 2.2.1 / VZ**, using the 4/8/40 profile. This was a separate disposable evaluation namespace with no host mounts, host clipboard sharing, agent forwarding or application-port forwarding.

Installed the **full `ubuntu-desktop` metapackage with its normal recommendations**, not just a window manager or browser kiosk. This was a cloud-image-plus-desktop provisioning experiment, not acceptance of the official interactive Desktop ISO installer.

A server/cloud image with `ubuntu-desktop` did **not** automatically seed App Center in this run. We installed it explicitly and tested GNOME Software as another normal graphical manager. The production recipe must handle graphical software-management readiness explicitly. APT/dpkg, Snap and their normal application installation are present; a full desktop UI still needs correct user-session activation, policy/privilege handling and catalog validation. The automation account must not gain blanket sudo merely to make a store button work.

## Browser availability and install policy

- Ubuntu default Firefox is available as an ARM64 Snap; that exact route was installed and exercised. Mozilla also publishes Linux ARM64 downloads and an official APT route for Debian/Ubuntu. The APT alternative was researched, **not installed/tested** in this VM. [Mozilla Linux downloads](https://www.firefox.com/en-US/download/linux/), [Mozilla installation guidance](https://support.mozilla.org/en-US/kb/install-firefox-linux).
- Ubuntu Chromium is available via the Canonical Snap route; Fedora packages Firefox and Chromium through its normal RPM ecosystem. Additional Chromium installs were **not** performed in this evaluation. [Chromium Snap](https://snapcraft.io/chromium), [Fedora Chromium packages](https://packages.fedoraproject.org/pkgs/chromium/chromium/).
- Google Chrome now has official Linux ARM64 **.deb and .rpm** downloads. This is no longer an x86-only assumption. It is a vendor/license/repository opt-in, not a silent Chromium substitute, and was **not installed** here. [Google's current ARM64 Linux requirements and installation instructions](https://support.google.com/chrome/answer/95346?hl=en&co=GENIE.Platform%3DDesktop).
- Do not promise every proprietary browser on ARM64. Microsoft's Linux distro list alone does not establish Linux ARM64 Edge availability; no Edge package/installation is verified here. [Microsoft's platform list](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-supported-operating-systems), [Arm's Edge architecture guide](https://learn.arm.com/install-guides/browsers/edge/).

Keep explicit browser identities/architectures and publisher trust. Ubuntu's Firefox package/source differs from Debian's firefox-esr; Fedora uses DNF/RPM, not the existing APT helper. These are profile migrations, not a simple image-URL override. Do not pass an Ubuntu image to the current Debian-only provisioning recipe and call that supported.

## Capture and input: proved feasibility, not a finished backend

GNOME 50/51 use Wayland. Xwayland can display legacy applications, but it does **not** turn scrot into a whole-desktop capture tool or xdotool/xclip into general native-Wayland input/clipboard control. Reusing those tools blindly would miss the shell/native apps or misroute actions.

The experiment ran a non-sudo GNOME user, headless Mutter with a fixed virtual monitor, guest session D-Bus and PipeWire. An explicitly experimental probe used Mutter's version-specific ScreenCast/RemoteDesktop methods to capture PNGs, move/click/drag/scroll, send physical keys, and transfer UTF-8 clipboard data entirely **inside Linux**. Native key/modifier and file-content checks passed. Pointer methods were acknowledged; semantic drag/drop, all buttons/combinations/layouts and international IME behavior are not comprehensively tested. Arbitrary Unicode keysyms lost characters in an early probe, so Unicode text used the actual guest clipboard instead. Earlier save-dialog/blank-browser attempts remain failed evidence, not passed tests.

The real Ubuntu PNG passed the existing `protocol.Frame.Validate` at **1280×800 / scale 1**. This verifies the shared image-format boundary only. The real AgentLinux guest protocol, stdio MCP server and live Kitty/web viewer have **not been operated end-to-end against this GNOME VM**. Their current functioning backend is still Debian/X11. No cloud or host-input fallback was introduced.

Mutter explicitly labels those D-Bus interfaces **private, without cross-version compatibility guarantees**. Do not ship the research probe as a maintenance-safe API just because it worked once. Prefer a maintained GNOME Remote Desktop backend (which already uses PipeWire/libei/Mutter) behind a local guest-only adapter, or the standard RemoteDesktop/ScreenCast/Clipboard portals with explicit session grants. Portal Start normally presents consent and restore tokens can expire; unattended headless bootstrap is a real design/validation task. A GRD/RDP route must be authenticated and constrained inside the guest, without an exposed host/LAN RDP listener or host clipboard/drive redirection.

Primary technical sources: [Mutter ScreenCast API and compatibility warning](https://github.com/GNOME/mutter/blob/50.0/data/dbus-interfaces/org.gnome.Mutter.ScreenCast.xml), [Mutter RemoteDesktop/clipboard/input](https://github.com/GNOME/mutter/blob/50.0/data/dbus-interfaces/org.gnome.Mutter.RemoteDesktop.xml), [GNOME Remote Desktop headless modes and PipeWire/libei](https://github.com/GNOME/gnome-remote-desktop/blob/50.0/README.md), [standard RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html), [standard ScreenCast portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html).

## Performance, provisioning and persistence

The prototype used software rendering, with no /dev/dri GPU device. Native ARM64 avoids an x86-emulation layer; this is **not** GPU passthrough or evidence of macOS-like animated performance. Before additional software-manager installs, a point-in-time guest sample showed ~2.79 GB used and ~5.51 GB available, and GNOME Shell RSS ~528 MiB. That is one workload/sample, not a minimum requirement or a comparison with Fedora. Do not infer FPS from individual PNG captures.

Cold full desktop/Snap provisioning exceeded Lima's built-in boot-script wait: start returned DEGRADED/error after **674.8 s**, while apt/Snap continued. We subsequently required the explicit install marker and a clean `dpkg --audit` before launching GNOME. Firefox's initial core Snap download was slow; App Center later installed in **9.9 s** after shared runtimes existed. These are network/cache-specific observations. A production profile needs truthful long-running provisioning/progress/recovery, not a relaxed fake-ready check.

Disk contents, user documents, installed apps, browser profiles and dconf settings belong on the persistent guest disk. Stop/up should preserve them; unsaved process state and clipboard ownership do not survive a reboot. The experiment's Unicode document was checked across an actual VM stop/start; detailed results are in verification.md/private persistence.json. The standalone compositor was a transient systemd unit and did not automatically restart: production GNOME session autostart/recovery remains unimplemented.

For Ubuntu, distinguish APT OS/app updates from Snap browser/store refreshes; a reboot/app restart may be needed. Fedora uses DNF/GNOME Software and a much shorter release lifecycle. Normal package installation must use explicit guest administration/per-user supported mechanisms, not a hardcoded reusable password or a privileged MCP installer. Reset remains explicit destructive reprovisioning, not a snapshot. Do not silently upgrade existing Debian machines into Ubuntu.

## Acceptance gate before changing the default

1. Add an explicit, versioned Ubuntu profile and 4/8/40 defaults with image integrity/provenance, correct package/browser mappings, Main/Universe/vendor maintenance policy and notices. Preserve old machine specifications/disks and use a separate state directory for evaluation.
2. Start a **managed complete GNOME session**, including user activation environment, snap launcher discovery, session services, software-manager catalog/auth flow and real first-frame readiness. Resolve the standalone App Center issue rather than treating a PID/window as ready.
3. Implement bounded guest-only Wayland capture/input/clipboard behind the common machine interface. Use stream metadata for coordinates/scaling, keep one latest frame with honest freshness/connection state, revoke frames on compositor/session restart, and release held input on failures. No host desktop/clipboard fallback.
4. Adapt app opening and explicit administration for Files/Ptyxis/Settings/Text Editor/Firefox plus optional supported browsers. Verify normal user application installation, updates, Unicode/clipboard, click/double-click/drag/scroll and key layouts.
5. Run real status → screenshot → act → verify through the official SDK and an actual agent client. Watch those exact guest changes in Kitty and the secure local web fallback; test resize, exit cleanup, stop/resume, desktop/service restarts and persistence. Reuse existing failure/limits/security tests, not compatibility claims based only on PNG dimensions.
6. Measure whole-VM and adapter CPU/RSS, end-to-end action-to-frame latency and active/static viewing under the proposed resources. Then select measured optimizations; no promised full-motion FPS before results.

**Decision:** select Ubuntu 26.04.1/GNOME 50 as the modern desktop direction, retain Debian/X11 as the verified working backend, and switch only after this gate. Fedora 45/GNOME 51 is the strongest upstream alternative, not a proven faster Mac backend. This choice prioritizes current visual completeness and a maintainable lifecycle, while funding the required Wayland work instead of staying on an old desktop to avoid it.
